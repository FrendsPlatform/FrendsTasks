## 1. Method signature

Exactly one public static method per task project. Everything else in the assembly is `internal`.

```csharp
using System.ComponentModel;
using Contoso.Salesforce.Query.Definitions;
using Contoso.Salesforce.Query.Helpers;

namespace Contoso.Salesforce.Query;

/// <summary>
/// Task Class for Salesforce operations.
/// </summary>
public static class Salesforce
{
    /// <summary>
    /// Executes a SOQL query against Salesforce.
    /// [Documentation](https://github.com/contoso/frends-tasks/blob/main/Contoso.Salesforce.Query/README.md)
    /// </summary>
    /// <param name="input">Essential parameters.</param>
    /// <param name="connection">Connection parameters.</param>
    /// <param name="options">Additional parameters.</param>
    /// <param name="cancellationToken">A cancellation token provided by Frends Platform.</param>
    /// <returns>object { bool Success, dynamic Data, object Error { string Message, dynamic AdditionalInfo } }</returns>
    public static async Task<Result> Query(
        [PropertyTab] Input input,
        [PropertyTab] Connection connection,
        [PropertyTab] Options options,
        CancellationToken cancellationToken)
    {
        try
        {
            ValidationHandler.Run(input, connection, options);
            cancellationToken.ThrowIfCancellationRequested();

            // task logic; pass cancellationToken to every awaited call

            return new Result { Success = true, Data = data, Error = null };
        }
        catch (Exception ex)
        {
            return ex.Handle(options);
        }
    }
}
```

Notes:
- `[PropertyTab]` is `System.ComponentModel.PropertyTabAttribute` — no Frends-specific NuGet dependency is needed for the attributes.
- `CancellationToken` is always the last parameter and is never decorated. Accepting it and then ignoring it is a common defect: a Process that is stopped mid-run will hang on the Task. Thread it through every `await` and long loop.
- Async is fine and preferred for IO. Do not block with `.Result` or `.Wait()`.
- `ValidationHandler.Run(...)` (generated by the template) runs the DataAnnotations attributes on every tab object and throws a `ValidationException` listing all failures. Call it first so bad input fails before any side effects, and prefer declarative `[Required]` / `[Range]` / `[RequiredIf]` attributes over hand-written guard clauses — the attributes also drive the Control Panel UI.

## 2. Parameter tabs

Each tab is its own class, decorated on the parameter with `[PropertyTab]`.

| Tab | Contains |
|---|---|
| **Input** | Always present, always first. Parameters essential for the task to function. |
| **Connection** | API URLs, access tokens, client IDs and secrets, connection strings. Use when credentials would otherwise bloat Input. Database connection strings belong here without exception. |
| **Options** | Additional/optional behaviour configuration. Never connection-related parameters. |

There are **no** Source and Destination tabs — their connection parameters go to Connection. If a download/upload task genuinely has many per-side parameters, group them within Input and Connection rather than reintroducing those tabs.

Options must always include:

```csharp
public class Options
{
    /// <summary>
    /// Whether an exception is thrown when the Task fails. When false, the failure is reported in the Result instead.
    /// </summary>
    /// <example>true</example>
    [DefaultValue(true)]
    public bool ThrowErrorOnFailure { get; set; } = true;

    /// <summary>
    /// Custom message used instead of the default error message when the Task fails.
    /// </summary>
    /// <example>Failed to query Salesforce accounts</example>
    [DefaultValue("")]
    public string ErrorMessageOnFailure { get; set; } = "";
}
```

Useful UI attributes (all from `System.ComponentModel` / `System.ComponentModel.DataAnnotations`):

- `[DefaultValue(...)]` — pre-filled value in the Frends UI
- `[PasswordPropertyText]` — masks secrets such as tokens and passwords
- `[DisplayFormat(DataFormatString = "Text")]` — treat the field as literal text rather than a C# expression
- `[DisplayFormat(DataFormatString = "Json")]` / `"Sql"` / `"Xml"` — editor syntax highlighting
- `[UIHint(nameof(Property), "", value)]` — show a field only when another property has a given value

## 3. Parameter naming and descriptions

- PascalCase, descriptive but brief.
- Abbreviations only where common (file format names, `Api`, `Url`) and always PascalCased: `Csv`, `Url`, `Xml`.
- Whole words over contractions: `Arguments`, not `Args`.
- Disambiguate rather than generalise: `InputFilePath` / `OutputFilePath`, not `FilePath`.
- Do not repeat the system name in parameter names — the task is already `Contoso.Salesforce.Query`, so `SalesforceQuery` is redundant.
- Descriptions explain what the parameter does, not just what it is. Use-case examples are encouraged; external links are fine where genuinely informative.

## 4. Result object

```csharp
public class Result
{
    /// <summary>Whether the Task completed successfully.</summary>
    /// <example>true</example>
    public bool Success { get; set; }

    /// <summary>Rows returned by the query.</summary>
    /// <example>[{"Id":"001","Name":"Example Oy"}]</example>
    public dynamic Data { get; set; }

    /// <summary>Error details when Success is false; null otherwise.</summary>
    public Error Error { get; set; }
}

public class Error
{
    /// <summary>Human-readable error message. Always present when Error is set.</summary>
    /// <example>Failed to query Salesforce accounts: request timed out</example>
    public string Message { get; set; }

    /// <summary>Structured details about what went wrong.</summary>
    public dynamic AdditionalInfo { get; set; }
}
```

Naming the payload:
- Weakly-defined data (database rows, arbitrary API payloads) → `Data`
- Known shape → semantic name: `FilePaths`, `FileExists`, `Content`, `StatusCode`, `Body`
- Properties whose content is undefined are `dynamic` and hold a `JToken` — this is what Processes expect for JSON.

`AdditionalInfo` should describe the problem as precisely as possible, and does **not** have to be `dynamic` — use a concrete type when the shape is known and reserve `dynamic` for genuinely unknown structures. For a multi-file copy, include the file names that failed and the underlying exceptions so a developer can debug. When no meaningful message can be produced, or the outer try/catch fires, put the exception itself in `AdditionalInfo`.

Do not put PII or secret values (tokens, connection strings, request bodies containing personal data) into `Message` or `AdditionalInfo` — those surface in Process Instance logs. Include identifiers and status codes instead.

## 5. Error handling

The template generates `Helpers/ErrorHandler.cs` as an extension method — use it as-is rather than reimplementing it. Note this differs from the older snippet in the Task Development Guidelines PDF (`ErrorHandler.Handle(ex, throwOnFailure, message)`); the template version is current and additionally handles cancellation.

```csharp
internal static class ErrorHandler
{
    internal static Result Handle(this Exception exception, Options options, bool throwCanceled = true)
    {
        ThrowIfCanceled(exception, throwCanceled);
        if (options.ThrowErrorOnFailure) ThrowBaseException(exception, options.ErrorMessageOnFailure);

        return ReturnResult(exception, options.ErrorMessageOnFailure);
    }

    private static void ThrowIfCanceled(Exception exception, bool throwCanceled = true)
    {
        if (throwCanceled && exception is OperationCanceledException) throw exception;
    }

    private static void ThrowBaseException(Exception exception, string customMessage = null)
    {
        if (string.IsNullOrEmpty(customMessage))
            throw new Exception(exception.Message, exception);

        throw new Exception(customMessage, exception);
    }

    private static Result ReturnResult(Exception exception, string customMessage = null)
    {
        var errorMessage = string.IsNullOrEmpty(customMessage)
            ? exception.Message
            : $"{customMessage}: {exception.Message}";

        return new Result
        {
            Success = false,
            Error = new Error { Message = errorMessage, AdditionalInfo = exception },
        };
    }
}
```

Behaviour this encodes, and the reasons it matters:

- **The original exception is always the inner exception.** Losing the stack trace makes Process Instance View useless for diagnosis.
- **`OperationCanceledException` is rethrown first**, before `ThrowErrorOnFailure` is consulted. A cancelled Process is a normal stop, not a Task failure, and must not be reported as `Success = false`. The `throwCanceled: false` overload exists for the rare Task that treats cancellation as a real failure — justify it if you use it.
- **`ErrorMessageOnFailure` prefixes rather than replaces** the underlying message in the non-throwing path, so context is added without discarding the cause.

If a Task needs richer error detail, extend `Error.AdditionalInfo` with a concrete type rather than changing the handler's control flow. The template types `AdditionalInfo` as `Exception` and flags it with a TODO — strong typing is preferred wherever the shape is known.

## 6. Multi-operation tasks

For tasks doing several operations (uploading many files, updating several partitions):

1. If one operation fails, continue with the rest when that is logically sound.
2. Set `Success = false` and include **all** failed operations in `AdditionalInfo`.
3. If `ThrowErrorOnFailure` is `true`, still complete the remaining operations, then throw at the end.

This ordering matters: throwing on the first failure loses the information about which of the remaining items would have succeeded.

## 7. Resource disposal

Some resources cannot be released during execution (connection pools, native handles, background listeners). Hook the assembly load context unload so the Agent does not leak them between Task versions:

```csharp
public static class MyTaskClass
{
    static MyTaskClass()
    {
        var currentAssembly = Assembly.GetExecutingAssembly();
        var currentContext = AssemblyLoadContext.GetLoadContext(currentAssembly);
        if (currentContext != null)
            currentContext.Unloading += OnPluginUnloadingRequested;
    }

    private static void OnPluginUnloadingRequested(AssemblyLoadContext obj)
    {
        // Dispose resources

        obj.Unloading -= OnPluginUnloadingRequested;   // unwire event
    }
}
```

Use this only where per-execution `using` blocks genuinely cannot do the job.

## 8. Task-type specific layouts

### Databases
- Query input field is always named `Query`.
- Return `Data`, plus `RecordsAffected` when the database itself reports it (updates/deletes).
- **Connection string on the Connection tab.**
- Input: `Query`, then `Parameters`.
- Options: transaction isolation level, command timeout, etc.
- Parameterise queries — string-concatenated SQL is an injection defect, blocking in review.

### REST API tasks
- Input order: `Method` (if applicable), `Url` / `Domain`, `ApiVersion` (if applicable), `Message`.
- Credentials → Connection.
- Result base structure: `Body`, `StatusCode`.
- Validate/allow-list the target host where the task is not a general-purpose HTTP client, to avoid it becoming an SSRF pivot.

### Converters
- Input parameter carries the source type name: `Json`.
- Result carries the target type name: `Xml`.
- Disable DTD/external entity resolution on XML parsing.

### File operations
- Input: local filesystem info (source/destination paths) first, then remote info (target upload folder).
- File conflict handling parameter is named `ActionOnExistingFile` and lives on Input.
- Connection: server info (SFTP, Azure Data Lake connection details).
- Single-file tasks use full paths — `InputFilePath`, `DestinationFilePath` — rather than splitting directory and filename.
- Results: read tasks return `Content`; write/move/rename/download/upload return `FilePath(s)` or `Url`; list and delete return `FileName(s)`.
- Canonicalise and constrain paths — a caller-supplied `../` traversal should not let the task write outside the intended directory.
