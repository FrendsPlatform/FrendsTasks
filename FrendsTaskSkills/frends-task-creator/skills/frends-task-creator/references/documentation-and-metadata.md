## 1. XML documentation

The Frends Control Panel renders XML docs directly into the Task's parameter editor, so documentation quality is user-facing UI, not developer courtesy.

Requirements:
- All public members documented.
- All parameters and result properties documented **with `<example>` blocks**.
- The task's `<summary>` links to its README in markdown: `[Documentation](link)`.
- For custom tasks the link points at the **owning organisation's** repository or docs site. `https://tasks.frends.com/tasks/...` only resolves for the official Frends catalog and must not be used.
- Extended documentation goes in a custom `<frendsdocs>` tag, never in `<summary>` — long summaries break the Frends UI layout.
- Markdown is supported (and encouraged) inside both `<summary>` and `<frendsdocs>`.
- Do **not** use `<cref>` or similar reference tags inside documentation text — they are not resolved in the rendered output.

Data structures in `<returns>` use this compact form:

```
object { bool Success, string Error }
object { bool Success, object[] Messages { string MessageId, string MessageText } }
```

Break large objects across newlines for readability.

Example:

```csharp
/// <summary>
/// Reads a blob from Azure Blob Storage.
/// [Documentation](https://github.com/contoso/frends-tasks/blob/main/Contoso.AzureBlob.Read/README.md)
/// </summary>
/// <frendsdocs>
/// Reads a single blob and returns its content as a string.
/// Large blobs are streamed; the whole content is still materialised in memory, so avoid
/// this Task for multi-gigabyte blobs and use a download Task instead.
/// </frendsdocs>
/// <returns>object { bool Success, string Content, object Error { string Message, dynamic AdditionalInfo } }</returns>
```

## 2. FrendsTaskMetadata.json and migration.json

Both are generated by the template into the **task project folder** (next to the `.csproj`) and packed into the NuGet package.

### FrendsTaskMetadata.json

Tells Frends which method to expose when the package is imported.

```json
{
  "Tasks": [
    {
      "TaskMethod": "Contoso.Salesforce.Query.Salesforce.Query"
    }
  ]
}
```

`TaskMethod` is the fully qualified `<Namespace>.<Class>.<Method>`. Under the `<Party>.<SYSTEM>.<ACTION>` convention this reads as `Party.System.Action.System.Action` — repetitive-looking but correct.

The template already wires the packing and analyzer hookup in the csproj:

```xml
<Content Include="FrendsTaskMetadata.json" Pack="true" PackagePath="/" CopyToOutputDirectory="PreserveNewest" />
<AdditionalFiles Include="FrendsTaskMetadata.json" />
```

The `AdditionalFiles` entry lets `FrendsTaskAnalyzers` cross-check the declared method against the code at build time, which catches a mistyped `TaskMethod` before import rather than after.

The schema is owned by the platform and can gain fields between versions. If a generated file is rejected on import, take the current schema from the template rather than inventing properties.

### migration.json

Declares how Task parameters map across versions, so existing Processes can be moved to a new Task version without manual rework. Seeded at `1.0.0` with an empty migration list:

```json
[
  {
    "Task": "Contoso.Salesforce.Query",
    "Migrations": [
      { "Version": "1.0.0", "Description": "", "Migration": [] }
    ]
  }
]
```

Add an entry whenever a release renames a parameter, moves one between tabs, or otherwise breaks the contract — that is precisely the change class that forces a major version bump, and the migration entry is what spares consumers from re-configuring every Process by hand. This file is newer than the Task Development Guidelines PDF, which predates it.

## 3. csproj

The template generates this; the de-branding table in `template-output.md` lists the exact values to change. Result after correction:

```xml
<PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <Version>1.0.0</Version>
    <Authors>Contoso</Authors>
    <Copyright>Contoso</Copyright>
    <Company>Contoso</Company>
    <Product>Contoso Frends Tasks</Product>
    <PackageTags>Frends;Contoso</PackageTags>
    <PackageLicenseExpression>MIT</PackageLicenseExpression>
    <GenerateDocumentationFile>true</GenerateDocumentationFile>
    <Description>Executes a SOQL query against Salesforce.</Description>
    <PackageProjectUrl>https://github.com/contoso/frends-tasks</PackageProjectUrl>
    <RepositoryUrl>https://github.com/contoso/frends-tasks</RepositoryUrl>
</PropertyGroup>
```

Notes:
- `Copyright`, `Product`, `PackageProjectUrl` and `RepositoryUrl` ship pointing at Frends and **must** be repointed — leaving them misattributes ownership of your code.
- `PackageLicenseExpression` must match the licence actually chosen; for a proprietary internal task, drop it and use `PackageLicenseFile`.
- The package ID defaults to the assembly name, so it inherits `<Party>.<SYSTEM>.<ACTION>` automatically — no `PackageId` override needed, and none should be added that reintroduces a `Frends.` prefix.
- Never put connection strings, keys, or tenant URLs in the csproj.

Builds must produce no warnings, and the workflows run with `strict_analyzers: true`. The template sets `<NoWarn>CS1591</NoWarn>` with an inline comment explaining that StyleCop SA1602 already covers it — that comment is the pattern to follow. Any `#pragma warning disable` or added `NoWarn` needs a comment saying which warning, why it fires, and why muting is safe; an unexplained suppression is a review failure.

## 4. README.md

Technical setup for developers only. Not end-user documentation — parameter descriptions live in the XML docs and are rendered by the Control Panel; duplicating them here guarantees drift.

Include:
- Standard description and badges (main build, NuGet, licence, code coverage), pointed at the owning organisation's pipelines
- Anything special needed to start work: certificates, local trust setup, how to get the unit tests running
- How to obtain credentials for the target system, where such a path exists (a process, not the credentials themselves)
- Attribution required by dependency licences
- Docker/test-account setup if the tests need it

The repository root `README.md` links to each task's `README.md`.

## 5. CHANGELOG.md

Kept current with every edit; every functional change is reflected. Uses the [Keep a Changelog](https://keepachangelog.com) format. The template already packs it (`<Content Include="../CHANGELOG.md" PackagePath="/" Pack="true"/>`) — keep that. Without it Frends falls back to fetching the changelog from the repository, which only works if the repo follows the standard task structure.

Write for the integration developer consuming the Task, not for the committer:
- Not: "refactored some code in MyBestClass.cs"
- Yes: the functional reason for the change, or a plain "Code cleanup" when nothing functional changed

Breaking changes always describe the upgrade path:

```
- [Breaking] Moved parameter XYZ to Options tab
  - To upgrade to the new version make sure to select the
    same value on the Options tab as it was on on the Input tab.
```

## 6. Versioning

Three-part `MAJOR.MINOR.PATCH`, e.g. `1.2.4`.

**Major — breaking.** Non-exhaustive:
- Moving a parameter between tabs (e.g. Input → Options)
- Renaming a parameter, including fixing a typo like `ConnectionStrung` → `ConnectionString`
- Removing or renaming a tab
- Adding a parameter with no default that reproduces the old behaviour, i.e. altering behaviour

**Minor — non-breaking.**
- Documentation fixes and improvements
- New parameters whose defaults preserve existing behaviour

**Patch — developer/testing.** Frends refuses to import the same Task version twice, so bump this while iterating against a tenant.

Every major bump should come with a `migration.json` entry describing how existing Process configurations map onto the new parameters, and a CHANGELOG entry spelling out the manual steps.

Prefer designing changes to be non-breaking: check whether a new parameter can have a default that preserves current behaviour. But do not pick a harmful default just to dodge a major bump — a sane default beats a compatible one, and if they conflict, take the breaking change and document the upgrade.
